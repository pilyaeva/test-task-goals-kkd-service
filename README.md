## Архитектура

Пакеты `com.example.testtaskgoalskkd`:

- `api` - контроллеры, record-DTO, единый обработчик ошибок (`GlobalExceptionHandler`). Бизнес-логики нет, к сервисам обращение через интерфейсы.
- `application` - сервисы (`RunService`, `KkdSummaryService`, `IssuesService`): сценарии, метрики, дельта.
- `domain` - сущности и бизнес-правила: `domain/quality` (правила), `QualityMetrics` (формулы метрик).
- `infrastructure` - репозитории Spring Data JPA и конфигурация.

**Где живут правила.** `domain/quality`: `QualityRuleEngine` получает список `GoalSnapshot` (цель, ответственный, статус, КР с весом и датой обновления) и дату снимка, возвращает список `DetectedProblem` (код правила и цель).

**Как создаётся прогон.** `POST /api/runs`: сервис читает активные цели с КР, вызывает движок правил, сопоставляет проблемы со справочником `rules` и в одной транзакции сохраняет `runs` и `run_problems`.

**Как считаются метрики** (`GET /api/kkd/summary`). Набор подразделений = выбранное + все вложенные (рекурсивно по `parent_department_id`). Берутся цели этих подразделений и их проблемы в текущем и предыдущем прогоне. Предыдущий прогон - с ближайшей более ранней `snapshot_date` (строго меньше). Три метрики, округление до 1 знака `HALF_UP`:

- `clean_goals_share` - доля целей без проблем (рост - лучше);
- `issues_per_goal` - проблем на одну цель (снижение - лучше);
- `critical_goals_share` - доля целей хотя бы с одной critical-проблемой (снижение - лучше).

`delta = value − previous`, `trend` - `better` / `worse` / `same` с учётом направления улучшения. Если целей нет, все значения 0 (без деления на ноль). `issues_by_severity` - количество проблем по важности в обоих прогонах.

**Как считается дельта между прогонами.** Проблема идентифицируется парой (правило, цель). `new` - пары есть в текущем прогоне и нет в предыдущем, `persisting` - есть в обоих, `resolved` - были в предыдущем и нет в текущем. Если предыдущего прогона нет, то `previous` и `delta` метрик равны `null` (не 0), `trend = same`, а все проблемы считаются новыми.

**Ошибки.** Единый формат `{"error": {"code", "message"}}`.

## Запуск

```bash
cp .env.example .env   # заполнить DB_PASSWORD
docker compose up --build
```

Поднимаются PostgreSQL и сервис; при старте сервис накатывает миграции Liquibase и стартовые данные (25 целей, 2 прогона).

```bash
./mvnw test            # тесты (для интеграционных нужен Docker: Testcontainers)
```

## Миграции: накат → откат → повторный накат

Миграции - Liquibase (`src/main/resources/db/changelog/`), у каждого changeSet есть `--rollback`.
Ручная проверка на запущенной через `docker compose up` БД (порт 5432 проброшен на хост):

```bash
export DB_PASSWORD=<значение из .env>   # PowerShell: $env:DB_PASSWORD="..."

./mvnw liquibase:update                              # накат (если сервис уже стартовал - ничего не делает)
./mvnw liquibase:rollback -Dliquibase.rollbackCount=4   # откат всех 4 changeSet'ов
./mvnw liquibase:update                              # повторный накат
```

Остальные параметры подключения: `-Dkkd.db.url=...`, `-Dkkd.db.user=...`.
Автоматическая проверка того же цикла - тест `MigrationRollbackTest`.

Локальный запуск без Docker для приложения (`./mvnw spring-boot:run`) читает параметры БД из переменных окружения `DB_URL`, `DB_USER`, `DB_PASSWORD` (см. `.env.example`); `DB_PASSWORD` обязателен.

Для запуска из IDEA или `./mvnw spring-boot:run`: сначала поднять только БД (`docker compose up -d postgres`), затем запускать приложение из корня проекта - параметры подключения подхватываются из `.env`.
