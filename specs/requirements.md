# Requirements

## Цель проекта

Сервис для расчёта и визуализации процедуры контроля качества данных (далее - ККД). В нём администраторы системы, руководители департаментов и ответственные за целеполагание в бизнесподразделениях на периодической основе (планируется еженедельно) проверяют качество данных по целям и ключевым результатам.

## Функциональные требования

### R-001. Получение списка прогонов

Пользователь может получить список прогонов: статус, дата снимка, с каким прогоном сравнивается, число найденных проблем.

Критерии приёмки:

1. [x] Сервис отдаёт список прогонов с полями в ответе: статус, дата снимка, с каким прогоном сравнивается, число найденных проблем.
2. [x] Если прошлого прогона нет, то дельта равна null.

### R-002. Получение метрик по целям и ключевым результатам

Пользователь может получить метрики по подразделению с текущим и прошлым значением, дельтой и признаком «лучше / хуже», разбивка проблем по важности и счётчики новых, сохраняющихся и исправленных. Метрики подразделения считаются с учётом дочерних.

Критерии приёмки:

1. [x] Сервис по `run_id` и `unit_id` отдаёт сводку: текущий прогон, прогон сравнения, подразделение, метрики, разбивку проблем по важности и счётчики `delta`.
2. [x] Возвращается минимум три метрики: `clean_goals_share`, `issues_per_goal`, `critical_goals_share`. У каждой есть текущее значение (`value`), прошлое (`previous`), дельта (`delta`) и признак `trend` (`better` / `worse` / `same`).
3. [x] Метрики и проблемы подразделения считаются с учётом всех его вложенных подразделений. Цели и проблемы соседних подразделений не учитываются.
4. [x] Прогоном сравнения считается прогон с ближайшей более ранней датой снимка. Прогон с той же датой не считается предыдущим.
5. [x] Если прогона сравнения нет, то `compared_to`, `previous` и `delta` метрик, а также `previous` и `delta` в `issues_by_severity` равны `null` (не 0), `trend` равен `same`.
6. [x] `trend` учитывает направление улучшения метрики: для доли корректных целей улучшение — рост, для остальных метрик — снижение.
7. [x] `issues_by_severity` содержит количество проблем в текущем и прошлом прогонах по каждой важности (`critical`, `major`, `minor`), которая встретилась хотя бы в одном из них. Порядок: от более критичной к менее.
8. [x] `delta` содержит счётчики `new`, `persisting`, `resolved`. Проблема считается той же самой, если совпадают правило и цель. Если прогона сравнения нет, то все проблемы считаются новыми.
9. [x] Если в подразделении нет целей, то сервис возвращает 200 и нулевые значения метрик без деления на ноль.
10. [x] Если прогон или подразделение не найдены, то сервис возвращает 404 с кодом `NOT_FOUND`. Если не указан `run_id` или `unit_id`, то возвращает 422 с кодом `VALIDATION_ERROR`. Формат ошибки: `{"error": {"code": "...", "message": "..."}}`.

### R-003. Получение списка проблем прогона

Пользователь может получить список проблем прогона с фильтрами по подразделению, правилу и важности и пагинацией.

Критерии приёмки:

1. [x] Сервис отдаёт проблемы одного прогона. В каждом элементе есть `id`, `rule_code`, `severity`, `goal_id` и `unit` (подразделение исполнителя цели). Проблемы других прогонов в выдачу не попадают.
2. [x] Поддерживаются необязательные фильтры по подразделению (`unit_id`), правилу (`rule_code`) и важности (`severity`). Фильтры комбинируются через «И», не переданный фильтр не применяется.
3. [x] Фильтр по подразделению учитывает его вложенные подразделения. Проблемы целей без исполнителя при таком фильтре не попадают в выдачу, а без него возвращаются с `unit = null`.
4. [x] Поддерживается пагинация: `limit` (1–100, по умолчанию 20) и `offset` (не меньше 0, по умолчанию 0). В ответе возвращаются `items`, `total` (число проблем по фильтрам без учёта пагинации), `limit` и `offset`.
5. [x] Порядок детерминирован: по важности (`critical`, `major`, `minor`), затем по `id`. Страницы не пересекаются и не теряют записи.
6. [x] Если проблем по фильтрам нет или `offset` выходит за пределы выборки, то сервис возвращает 200 с пустым `items`, а не 404.
7. [x] Если прогон, подразделение или правило не найдены, то сервис возвращает 404 с кодом `NOT_FOUND`. Если не указан `run_id`, `limit` или `offset` вне диапазона или не число, `severity` не из списка допустимых значений, то возвращает 422 с кодом `VALIDATION_ERROR`. Формат ошибки: `{"error": {"code": "...", "message": "..."}}`.

### R-004. Запуск прогона

Пользователь может запустить прогон ККД: правила применяются к активным целям и их КР, прогон и найденные проблемы сохраняются.

Критерии приёмки:

1. [x] `POST /api/runs` создаёт прогон со статусом `COMPLETED`, датой снимка — текущая дата, идентификатором `RUN-NNN` (максимальный номер + 1), и возвращает 201 с полями как у элемента `GET /api/runs`. Тело запроса игнорируется.
2. [x] Правила применяются только к целям со статусом `ACTIVE` и их ключевым результатам.
3. [x] Найденные проблемы сохраняются в `run_problems` с идентификаторами `PRB-NNN`; прогон и проблемы сохраняются в одной транзакции.
4. [x] Если для сработавшего правила нет записи в справочнике `rules`, то возвращается 500 с кодом `INTERNAL_ERROR`, ничего не сохраняется.

### R-005. Правила ККД

Реализованы четыре правила в отдельном компоненте, не зависящем от API и доступа к данным.

Критерии приёмки:

1. [x] `GOAL_NO_OWNER` (critical), `GOAL_NO_KR` (critical), `KR_WEIGHTS_SUM` (major), `KR_STALE_PROGRESS` (minor) работают по описанию в `design.md`, раздел «Алгоритмы».
2. [x] Границы проверены тестами: ровно 45 дней — не нарушение, 46 — нарушение; сумма весов сравнивается без допуска.
3. [x] Порядок результата детерминирован: по порядку правил, затем по `goal_id`.

## Нефункциональные требования

1. [x] Миграции Liquibase с откатом: накат → откат → повторный накат проходят без ошибок (`MigrationRollbackTest`).
2. [x] `docker compose up` поднимает PostgreSQL и сервис; миграции и стартовые данные (25 целей, 2 прогона, нарушения каждого правила) применяются при старте.
3. [x] Конфигурация через переменные окружения (`.env.example`).
4. [x] Все ошибки возвращаются в едином формате `{"error": {"code": "...", "message": "..."}}`.
